## 0. 一句话总纲

**快照不是数据库，是缓存。**

data/ 里的语料才是唯一真相源；快照只是"算过一遍的索引"存在磁盘上的
一份拷贝，随时可以扔掉重算。整份设计只有一个核心心态：一切决策都往
"简单、可验证、坏了就重建"的方向走，而不是"复杂、增量修补、尽量抢救"。

后面你会反复看到这个心态兜底：崩溃了？重建。看不懂了？删掉重建。
字节序跨机器？重建。搞不清哪层坏了？反正五类失败全部导向同一个动作
——重建。

## 1. 我们在解决什么问题

现状（M1 的 main）：每次启动都要跑一遍完整管线

```
load_documents  ->  chunk_documents  ->  build_index
   读文件             切块                 建倒排表+算BM25用数据
```

24 篇语料毫秒级无感。但语料涨到 59 篇（M2-③ 之后）、几百篇时，
每次启动都白算一遍同样的东西。

本质认识：**倒排索引是纯派生数据**。它由四样东西完全决定——
语料字节、分词规则、切块参数、索引语义。输入不变则输出不变。
"派生数据算一次存盘、下次直接读"是缓存问题的标准形态。

一个关键洞察（当时讨论过的预期管理）：启动时"读文件"这一步
**不可避免**——你必须知道语料变没变。持久化能省的只有
chunk + tokenize + build 三段**计算**，不是文件 I/O。

## 2. 存什么、不存什么（乙案）

三档方案：

| 档 | 内容 | 问题 |
|---|---|---|
| 只存倒排索引 | postings 等 | load 后 chunk.text 无法恢复（text 要从 content 切出来） |
| 全存 | 连 text、avgdl 都存 | 能用，但存了"廉价可重算"的东西：多占磁盘，多一份不一致的机会 |
| **乙案（裁定）** | 源事实 + 昂贵派生存，廉价派生不存 | — |

判据是 type.h 设计时（09-22 21:30）就立过的公式：**推导成本 x 使用频率**。

| 字段 | 性质 | 决定 |
|---|---|---|
| Document.content | 源事实（loader 之外没人能再生它） | 存 |
| Document.path / deleted | 源事实 / 运行时状态 | 存 |
| Chunk.begin/end | 切块的产物（要重切一遍才能再生，昂贵） | 存 |
| Chunk.text | 一次 substr 就能再生（廉价） | **不存**，load 时重建 |
| postings / chunk_lengths | tokenize+build 的产物（昂贵） | 存 |
| avg_chunk_length | 一次加法一次除法（廉价） | **不存**，load 时从 chunk_lengths 重算 |

两个重建细节，契约里都要有对应条款：

- text 重建：`content.substr(begin, end - begin)`——chunker.h 条款 3
  的原文，这就是"text 是 begin/end 的函数"的凭证。
- avgdl 重建：空索引必须得 0.0 而不是除零崩溃——indexer.h 条款 4
  规定了"0.0 for empty input"，load 侧要带同款守卫。

## 3. 为什么是自定义二进制（两堂课）

### 3.0 先补地基：内存、磁盘、STL 容器、二进制文件是什么

**两个仓库。** 内存（RAM）= 办公桌：程序运行时所有变量（docs /
chunks / index）都摊在这里，断电全蒸发。磁盘 = 档案柜：一切文件
（.cpp、.exe、data 的 .md、将来的 index.bin）长住这里，断电不丢。
文件夹只是操作系统在磁盘上搞的组织结构；**文件 = 磁盘上一段起了
名字的字节**。程序一关，内存蒸发——这就是 M1 每次启动都要重新
build_index 的原因，也是持久化要解决的事。loader.h 已经是一次
"磁盘 -> 内存"（ifstream 读 .md 变 content），save 是反方向。

**STL 容器的真实长相。** std::vector / std::string / std::unordered_map
这些标准库数据结构，本体只是个**小账本**（一个指向堆的指针 + 长度
+ 容量），真正的元素在堆上另一块：

```
[chunks 变量本身]              [堆上的真数据]
 ptr ─────────────────────→  Chunk0 Chunk1 ... Chunk76
 len = 77
```

unordered_map 更是"指针织成的网"（桶数组指针 -> 节点指针链）。
fwrite(&chunks) 写进文件的只是账本十几个字节，指针值是**本次运行
的堆地址**——像备份仓库只复印了门上的地址条，货一样没存；下次
运行按地址找过去已是别人家，这就是野指针崩溃。所以磁盘协议必须
**逐字段翻译**（先写个数 77，再逐个写 Chunk 的字段），读回来在
内存里**重新拼装**容器。save / load 就是这个翻译官。

**一切文件本质都是字节串。** "文本/二进制"不是两种物理文件，是
两种**解释约定**。实证（data 语料头 48 字节）：

```
23 20 5B 53 63 68 6F 6F 6C 20 43 54 46 5D ...
#     [  S  c  h  o  o  l     C  T  F  ]
```

按"每字节一字符"解释就是文本文件；exe / png 的字节按程序自定义
规矩解释，记事本打开乱码，就是二进制文件。存整数 1234 的对比：
文本 `31 32 33 34`（4 个字符），二进制 uint32 `D2 04 00 00`
（拿到的直接就是数）。快照内容是海量整数且只有程序自己读写，
不需要人读——选二进制。

**快照从哪来。** 格式自己定义（第 4 节布局图）、代码自己写
（persist.h + persist.cpp）、文件由我们的 exe 自己生成：第一次
启动 build 后 save() 把内存容器翻译成 index.bin 落盘；第二次启动
validate 可信后 load() 翻译回内存。没有外部工具参与。

### 3.1 最重要的一课：内存数据结构 ≠ 磁盘协议

直觉方案：把 InvertedIndex 整个 fwrite 到磁盘，下次 fread 回来。
**这是被红线禁止的**，原因按严重程度排：

1. `unordered_map<string, vector<Posting>>` 内部全是**指针**（桶数组、
   节点链表）。写盘写进去的是本次运行的堆地址；下次启动堆布局完全
   不同，读回来的指针全是野指针，一解引用就崩。
2. struct 有对齐 padding——编译器在字段间塞的空隙，不同编译器/
   平台塞法不同，你的"协议"其实没有定义。
3. size_t 是平台宽度类型（x64 = 8 字节，32 位 = 4 字节），换个平台
   读出来的宽度都不一样。

结论：磁盘上必须**逐字段编码**——每个整数用固定宽度类型
（uint32_t / uint64_t），每个字符串 = 长度前缀 + 原始字节，每个
vector = 元素个数 + 逐元素。读回来按同样的规矩逐字段解码，在内存里
**重新构造** STL 容器。磁盘协议是你们自己定义的字节流，和内存里
长什么样无关。

### 3.2 为什么不用 JSON / 文本格式

JSON 完全可行，人类可读还是优势。不选的理由：

- post ​ings 是几十万个整数对，文本表示体积 3-5 倍，解析还要逐字符扫
- 我们没有"人读快照"的场景——坏了就删掉重建，不存在手工修快照
- 项目纪律不引第三方库；手写一个 JSON 编码器（转义、引号、数字格式）
  比手写二进制编码器**更复杂**

二进制"不可读"对缓存不是缺点：它是给程序看的，不是给人看的。

## 4. 磁盘布局：24 字节头 + 载荷

```
偏移   大小   内容
---------------------------------------------------------------
0      8      magic: "MYRAGIDX"（8 个 ASCII 字节，无 \0 终止）
8      4      FORMAT_VERSION   (uint32)
12     4      PIPELINE_VERSION (uint32)
16     8      payload fingerprint (uint64, FNV-1a，盖住 24 之后全部字节)
---------------------------------------------------------------
24     ...    payload（载荷）:
              - CHUNK_SIZE, CHUNK_OVERLAP   (各 uint32)
              - documents: 个数 + 逐个
                  { id, path(长度+字节), content(长度+字节), deleted }
              - chunks: 个数 + 逐个
                  { id, document_id, begin(uint64), end(uint64) }   <- 无 text
              - postings: term 个数 + 逐 term
                  { term(长度+字节), posting 数 + 逐个 { chunk_id, tf } }
                  （term 按字节字典序写盘 —— 见第 8 节）
              - chunk_lengths: 个数 + 逐个 uint32
              - manifest: 个数 + 逐条
                  { path(长度+字节), content 指纹 uint64 }
                  （按字典序写盘）
```

三个说明：

- begin/end 磁盘上是 uint64——type.h 里它们是 size_t（平台宽度），
  这是"固定宽度磁盘协议"的直接论据（18:32 对账时抓的）。
- 头部 16 -> 24 字节：第 8 节之后的载荷指纹（19:08 拍板加入）。
  它堵的盲区：magic/版本/参数/manifest 五关全过，但载荷**中段**
  某个字节坏了（结构仍然解析得通）——没有指纹的话 validate 报 OK，
  load 静默加载出一份错误索引。加上后这种情况归入 BAD_FORMAT，
  "损坏 = cache miss"的红线才真正闭环。
- 这张图是实现施工卡级别的布局；persist.h 契约写的是语义条款
  （存了什么、按什么顺序判失效），不逐字节背书。

## 5. 三个"版本"，三个变化源（设计的灵魂）

快照会因三种完全不同的原因作废，各配一个维度、各配一个检测手段：

| 维度 | 回答的问题 | 放哪 | 谁改它 |
|---|---|---|---|
| FORMAT_VERSION | 磁盘布局变了吗（字段增删/顺序/宽度） | 头部 4B | 改 persist 格式时手动 +1 |
| PIPELINE_VERSION | 派生管线语义变了吗 | 头部 4B | 改任一管线语义时手动 +1 |
| manifest | 语料字节变了吗（增/删/改名/改内容） | 载荷 | 随语料自然变化，全自动 |

为什么 PIPELINE_VERSION 放 persist.h 而不放 atom_scan.h（18:47 裁定）：
它版本化的是 chunk -> tokenize -> index **整条链**的语义，不属于任何
单个模块；放在 scanner 旁边会误导"只有 scanner 改才 bump"。

它是全设计唯一需要"人记得去 bump"的零件（bump = 程序员黑话，手动
把版本号加一：PIPELINE_VERSION 从 2 改成 3，就这一下；FORMAT_VERSION
严格说也是手动，但改布局时你正在 persist.cpp 里、版本号就在手边，
而管线语义的触发点在 atom_scan/tokenizer/chunker，离 persist.h 很远，
没人提醒），所以契约里要带触发清单注释。漏 bump 的后果用一个具体例子感受：假如把 bigram 改成 trigram
而不 bump——validate 五关全过（语料没变、格式没变、参数没变），
load 出 bigram 时代的索引；查询端把词切成 trigram 去查 bigram 的
倒排表，全查不到。**没有任何报错**。静默错比崩溃坏得多。

PIPELINE_VERSION 与 BAD_PARAMS 的分工（容易混）：

- 分词/切块的**规则**变了（Han 范围、三明治、bigram 政策） ->
  bump PIPELINE_VERSION
- 只是参数**值**变了（CHUNK_SIZE 500 -> 800） -> 不用 bump，
  参数本身已入盘核对，validate 自动报 BAD_PARAMS

## 6. 失效检测：validate 的七问与八态

`validate(path, docs)` 按固定顺序自问，第一个不成立的就返回：

| 序 | 问题 | 不成立时返回 |
|---|---|---|
| 1 | 文件存在吗 | NOT_FOUND（首次启动，正常态，不是失败） |
| 2 | 打得开、读得动吗 | IO_ERROR（权限、被占用——文件本身没问题） |
| 3 | 前 8 字节是 MYRAGIDX 吗 | BAD_MAGIC（这根本不是我们的快照） |
| 4 | FORMAT_VERSION 支持吗 / 载荷指纹对得上吗 | BAD_FORMAT（新格式读不了 / 内容坏了截断了） |
| 5 | PIPELINE_VERSION 一样吗 | BAD_PIPELINE |
| 6 | CHUNK_SIZE / OVERLAP 一样吗 | BAD_PARAMS |
| 7 | manifest 与当前语料一致吗 | CORPUS_CHANGED |
| - | 全过 | OK |

两个设计点：

- **顺序写进契约**：多病共存时（既改了语料又换了版本）返回值必须
  确定，否则测试断言不稳定。顺序原则 = 便宜的头部检查在前，
  贵的语料比对在后。
- **为什么 validate 吃 docs 而不是自己去扫 data/**：main 反正要先
  load_documents（读文件不可避免），把现成的 docs 喂给 validate，
  在内存里对 content 算指纹比对 manifest——persist 不走目录、
  不依赖 loader、零重复 I/O。"哪些文件算语料"的定义权（递归、
  .md/.txt、字典序）留在 loader 一处，不出现第二事实源。

纯度条款（18:55 裁定）：manifest 只比 **path + content**，不比
id / deleted——manifest 回答的是"磁盘上的输入语料是不是同一批字节"，
不回答"运行时状态一不一样"。当前 loader 读出的 docs 只是验证用的
**现实探针**；验证通过后运行时状态由 load 从快照恢复（main 侧变量
命名最好区分这两个 docs）。

enum 而非 bool 的价值：main 能打一行人话（"快照弃用：语料已变化，
重建中"），而测试直接断言 enum 值，不用去抓日志文本。

## 7. 指纹：FNV-1a 64 + 排序比对

FNV-1a：一种非加密哈希，一遍扫描把任意长度字节流折叠成 64 位数。
特点：极快、实现十几行、零依赖。它的定位是**内容指纹
（content fingerprint）**——检测**意外**改动（磁盘坏字节、文件被
编辑、写盘写了一半），不防**恶意伪造**。这是缓存场景的正确选择；
加密哈希（SHA 系）在这里是杀鸡用牛刀。

manifest 的相等判定：`[{path, 指纹}]` **按字典序排好后逐条相等**。
一次比较覆盖全部四种语料变化：

```
新增文件   ->  排序后列表多一条      ->  不相等
删除文件   ->  少一条                ->  不相等
改名       ->  旧路径少一条 + 新路径多一条（等价于删+增）  ->  不相等
改内容     ->  同 path 指纹不同      ->  不相等
```

排序不只为了比对，也是为了写盘确定性（下一节）。

## 8. 确定性序列化：同一状态 -> 永远同一字节

问题源头：`unordered_map` 的遍历顺序不确定（哈希表实现细节，连同一
进程内插入顺序不同都会导致遍历序不同）。按遍历序写盘，同一份索引
存两次，字节不一样。

裁定：**postings 按 term 的字节字典序写盘**。收益链条：

```
同一索引状态 -> 永远同一字节序列
    -> save -> load -> save，两次快照文件逐字节相等（最硬核的测试）
    -> 排查问题可以直接 diff 两份快照
    -> manifest 同款排序，一箭双雕
```

头部**没有时间戳**也是同一逻辑：任何时间性、随机性的字节都会
毁掉确定性。想记"这份快照什么时候存的"？不记。需要的话看文件
mtime（那是文件系统的事，不在协议里）。

## 9. 原子替换：写一半崩溃不能毁掉旧快照

save 直接打开正式文件开写 = 崩在中间 = 旧快照毁了、新的又不完整。
虽然缓存心态下"下次重建"也能接受，但白白丢缓存还留隐患。

标准做法（三步）：

```
1. 写临时文件   index.bin.tmp（正常打开正常写）
2. 写完、关闭   （数据完整落盘）
3. rename tmp -> index.bin   （同一磁盘卷上 rename 是原子操作）
```

Windows 细节（实现卡里验证）：POSIX 保证 rename 覆盖已存在目标，
Windows 的行为要实测；兜底 = 先 remove 再 rename。两步之间崩 =
快照没了 = 下次重建——可接受，缓存心态再次兜底。

## 10. load：全有或全无

契约条款：**load 成功时一次性交付三个输出；失败时三个输出保持原状。**

反面场景（为什么需要这条）：读快照读到一半失败——

```
docs    被改了一半
chunks  只读出几十个
index   还是调用前的旧值
```

这种"半套状态"比失败本身危险：程序可能拿着混合状态继续跑，
错得悄无声息。实现思路（施工卡再展开）：全部读到局部临时变量，
每一步都成功，最后一步才交付到输出参数。

load 内部还做三件事：

1. substr 恢复每个 chunk.text（按 document_id 找到 content，
   `substr(begin, end - begin)`）
2. 从 chunk_lengths 重算 avgdl（空表 -> 0.0，同 indexer.h 条款 4）
3. 顺手复核头部（magic/版本/参数，24 字节比对近乎免费）——
   main 的 validate -> load 序列实际不会撞上，但 load 将来被单独
   调用（比如 GUI 直接给路径）时也安全

异常政策（19:08 讨论定）：**三个函数全不抛**，失败全走返回值
（save/load 返 bool，validate 返 enum）。同 search 不抛的先例——
调用方拿到确定的返回值才好写。

## 11. API 分工与 main 流程

persist 是哑的（只搬数据，不做策略）：

```
save(path, docs, chunks, index)              -> bool    运行时状态 -> 快照
validate(path, docs)                         -> enum    旧快照能不能信 + 为什么
load(path, docs, chunks, index)              -> bool    可信快照 -> 完整即用状态
```

策略（"信不信、要不要重建"）在 main：

```
docs = load_documents(data)                     // 读文件，不可避免
st  = validate(idx_path, docs)
if (st == OK && load(idx_path, docs, chunks, index))    // 双保险：
    ;                                                  // validate 过但 load 半路
else {                                                  // IO 失败 -> 兜底重建
    chunks = chunk_documents(docs)               // fresh build
    index  = build_index(chunks)
    save(idx_path, docs, chunks, index)          // 失败仅警告，不致命
}
// 查询循环照旧
```

validate 与 load 不合并（不搞 validate_and_load）：前者是"能不能信"
的**策略判断**，后者是**数据搬运**。分开，main 才能自由组合——
将来 GUI 可能有自己的策略（比如弹窗问用户）。合并了，策略和搬运
又粘死在一起。

## 12. 这份设计刻意不管什么（边界）

- **M2-③ 增量建库**：改一篇语料只重算那一篇、postings 局部手术——
  与"哑 persist"是两种设计，不提前混入。现在是全量重建，简单正确。
- **M2-④ 墓碑与 manifest 的交互**：被软删文档的文件如果移出 data/，
  manifest 失配触发重建会把 id 序列洗牌——到 M2-④ 再裁。
- **并发/多进程锁**：单机单进程，不存在这个问题。
- **加密、压缩**：不需要；将来要压缩 = 改磁盘布局 = bump
  FORMAT_VERSION，门留着。

## 13. FAQ（第一次做持久化最容易问的）

**Q: 快照比语料本身还大（content 整存了一份），正常吗？**
A: 正常。持久化省的是启动**计算时间**，不是磁盘空间。真在意体积，
   M5 可议 zstd 压缩（届时 bump FORMAT_VERSION）。

**Q: 为什么不用 SQLite？**
A: 它解决的问题（局部更新、事务、并发、SQL 查询）我们一个都没有；
   我们的需求是"整存整取一个缓存文件"，引数据库依赖（项目纪律：
   核心自研）换不来任何收益。

**Q: 手滑删了快照文件会怎样？**
A: 下次启动 validate -> NOT_FOUND -> 重建 -> 再存。零损失。
   推论：今后任何"索引行为诡异"的问题，第一急救招就是删快照重跑
   ——排掉"缓存坏了"这个变量。

**Q: 改 BM25 的 k1 / b 要 bump 哪个版本？**
A: 都不用。k1/b 是查询期参数，根本不在索引里（索引只存 postings
   和 chunk_lengths）——乙案"只存派生物"的红利。改 CHUNK_SIZE/
   OVERLAP 也不用 bump：参数已入盘核对，自动 BAD_PARAMS。

**Q: validate 和 load 都要读一遍快照文件，浪费吗？**
A: 本地磁盘顺序读一份几百 KB 的文件是微秒级，而换来的接口边界
   （策略与搬运分离）值这个价。不值得优化的事就不优化（优化三规则）。
